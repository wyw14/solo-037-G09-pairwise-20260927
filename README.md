# WaveLab

WaveLab is a local HTTP service for tow-tank experiments. The original equipment and interlock pages expose a fixed commissioning diagnostic scenario. Operator measurements are a separate live data path.

Set `WAVELAB_DATA_DIR` to choose the archive directory (default `data/wavelab`). `POST /api/measured-runs` accepts `name`, `model_name`, `section`, and `carriage`, plus optional tow conditions `tow_speed` (m/s, > 0), `wave_condition` (e.g. `calm` or `regular:H=0.1,T=1.5`) and `loading` (loading condition/draught). The three conditions are optional but must be supplied together: a run with none is accepted but cannot join a comparable repeatability group; a run with only some is rejected. Conditions are fixed when the run is created. `POST /api/measured-runs/{id}/evidence` accepts `kind` (`wave_time` or `force`), `source_id`, finite `value`, and `recorded_at` in RFC3339 form. `GET /api/measured-runs`, `GET /api/measured-runs/{id}`, and `GET /api/measured-runs/{id}/analysis` return the supplied records and wave/force summary. Measurements are committed to `operator-measurements.json` before they are published in memory, and are reloaded when the service restarts. Runs stored by older versions (no `conditions` key) deserialize as unconfigured and are blocked from cross-run comparison rather than assumed to share conditions. The archive does not automatically grant a safety permit or drive hardware.

### Trial groups and repeatability

A trial group is a named, persisted set of measured runs that an operator wants checked as repetitions of the same set-up.

- `GET /api/trial-groups` lists groups; `POST /api/trial-groups` accepts `{"name": "...", "run_ids": [...]}` (at least two distinct, existing runs — conditions are deliberately *not* pre-validated, so mismatched tows can still be grouped and diagnosed); `GET /api/trial-groups/{id}` returns one group. Groups persist to `trial-groups.json` (same atomic write/reload behaviour as the measurement archive) and the page is served at `/trial-groups`.
- `GET /api/trial-groups/{id}/consistency` always returns 200 when the group exists, even when the runs are not comparable: blocking reasons are data in the body, not HTTP errors. A missing group is 404.

The report never returns a single average score. `comparable` is true only when every member exists, there are at least two members, and all six compared fields (`model_name`, `section`, `carriage`, `tow_speed`, `wave_condition`, `loading`) are configured and equal. Otherwise `blockers` names each problem (`member_count`, `missing_run`, `conditions_unconfigured`, `condition_mismatch`) and `condition_differences` lists, per field, each run's value (null when unconfigured); cross-run wave/force metrics are withheld, while per-run summaries are always returned. An `aborted` run and evidence gaps produce `advisories`, not blockers; a source present on only some runs is shown in the coverage matrix, and pairwise metrics for that pair report `missing_source`.

Per-source, per-pair metrics: each run's series is independently time-normalized onto a 101-point `[0,1]` grid with linear interpolation (shape comparison; true time spans appear in the coverage matrix). `pearson` measures shape agreement; `nrmsd = rms(a-b) / ((range(a)+range(b))/2)` is symmetric in run order; `mean_delta` and `rms_delta` always accompany a valid resampling. Undefined metrics are JSON null with an explanatory `status`: `scalar` (both sides are single points, e.g. one force reading per tow — only `mean_delta` applies), `insufficient_sample`, `zero_span`, `undefined_zero_variance`, `undefined_zero_amplitude`, `missing_source`. The coverage matrix reports per source/run the sample count, time span, and a sampling-gap flag (`max gap > 2 × median gap`).

The `internal/probe`, `internal/force`, `internal/permit`, `internal/carriage`, `internal/track`, `internal/wave`, `internal/absorber`, and `internal/journal` packages provide component logic for further work. Their diagnostic use does not imply that the original HTTP pages accept real sensor streams.
